# parent-child-force-correction

## Summary

Reproduce Nemesis's parent-child synchronisation by computing second-order kick-drift-kick correction kicks that couple the decoupled children systems to the Ph4-integrated parent set, synchronising the micro- and macro-state at each bridge step.

## When to use

Use when reconstructing or testing the coupling stage of a multi-scale hierarchical N-body integrator: you have a parent particle set plus isolated child systems (e.g. planetary systems identified by syst_id > 0) that must be re-synchronised via correction kicks at each bridge time step.

## When NOT to use

- When comparing against a direct N-body integration — set RUN_NEMESIS = 0 in tests/cluster_test/run_cluster.py instead of applying the correction-kick coupling
- When the child integrators differ in code parameters (internal time-step) from the parent or direct run, making the comparison invalid
- When stellar evolution or the galactic tidal field is enabled during the convergence test — the README advises turning both off for a clean performance/error comparison

## Inputs

- AMUSE particle set with syst_id attribute (children: syst_id > 0), generated by examples/basic_cluster/particle_initialiser.py into ICs/
- Bridge time step (dtbridge, e.g. 500 yr) and end time (--tend, e.g. 0.1 Myr)
- Parent integrator (Ph4) and child integrator instances with identical code internal time-step (0.1)

## Outputs

- Corrected (kicked) parent and child particle states synchronised at each bridge step
- kdk_convergence_errors.csv: energy error versus bridge time-step table
- Fitted log-log slope of energy error versus bridge step (expected ~2 for second order)

## How to apply

Categorise parents and children using the syst_id particle attribute (children have syst_id > 0) as done in src/hierarchical_particles.py, then extract the correction routines from src/grav_correctors.py and the _parent_worker/_sub_worker routines of src/nemesis.py. Compile the C++ correction-kick routines under src/cpp with make, since these calculate the kicks synchronising the micro- and macro-state, and run the compiled extension from the same Python environment used to build it. Integrate the parent set with Ph4 and each child system in isolation, applying the second-order kick-drift-kick correction kicks at every bridge step (cluster test suggests a 500 yr bridge time, 0.1 Myr end time, code internal time-step 0.1). Validate by halving the bridge step over a 0.1 Myr run, fitting log(energy error) versus log(bridge step) to confirm approximately second-order convergence, and benchmarking against a direct Ph4 run (RUN_NEMESIS = 0).

## Examples

```
cd src/cpp && make && python main.py --tend=0.1Myr --dtbridge=500yr
```

## Evaluation signals

- log(energy error) versus log(bridge step) slope is approximately 2, confirming second-order convergence of the kick-drift-kick scheme
- Energy error decreases monotonically as the bridge time step is halved (500 yr -> 250 yr -> ... over a 0.1 Myr run)
- Corrected Nemesis run yields total-energy behaviour indistinguishable from a direct Ph4 N-body run (RUN_NEMESIS = 0) with identical internal time-step 0.1
- Every child particle with syst_id > 0 is reassigned/contributing to exactly one parent correction kick per bridge step (checked via np.unique(bodies.syst_id))
- Compiled C++ extension runs in the same Python environment as the simulation (a mismatch crashes correction kicks)

## Limitations

- Runs can be resumed, but changing simulation parameters while resuming proceeds with only a warning, which can silently invalidate a convergence series
- Nemesis uses sockets (not MPI) for child subsystems because hibernation/resumption cycles destabilise MPI workers; suspending workers mid-communication can crash the run
- Any change to workers (_parent_worker, _sub_worker, etc.) must be mirrored in _worker_list or run-time handling breaks
