# wallclock-runtime-profiling

## Summary

Profile how Nemesis wall-clock time scales with the number of child (planetary) systems, specifically testing parallel saturation once systems exceed available cores. Uses Ph4 as identical parent/child integrator with internal time-step 0.1, sweeping excess-system counts and fitting a linear runtime model.

## When to use

Use when benchmarking Nemesis scalability in wall-clock time as a function of the number of child systems, especially to verify the at-worst-linear growth regime beyond the number of available cores.

## When NOT to use

- The goal is accuracy validation (e.g. von Zeipel–Lidov–Kozai secular evolution or comparison against direct N-body Ph4) rather than performance scaling measurement.
- The number of child systems does not exceed the number of available cores, so the linear-excess regime under test is never entered.
- Workers use integrator configurations or code parameters that differ between parent and child, making wall-clock comparisons across excess counts non-comparable.

## Inputs

- Particle set of planetary (child) systems generated by examples/basic_cluster/particle_initialiser.py, saved in the ICs/ folder
- Nemesis repository (github.com/ErwanH29/nemesis) with C++ correction-kick extension compiled via src/cpp/make
- Series of runs varying the number of child systems beyond the available core count

## Outputs

- timing_scaling_table.csv with one wall-clock runtime row per excess-system count
- Least-squares linear fit of wall-clock time vs. number of excess systems, with slope and goodness of fit
- sim_stats/ runtime diagnostics files per run

## How to apply

Generate a cluster of planetary systems with examples/basic_cluster/particle_initialiser.py (AMUSE), saving the particle set to ICs/. From the project root run 'python main.py' with Ph4 as both parent and child integrator with an identical internal time-step of 0.1, disabling the galactic field, stellar evolution, and child collisions, while sweeping the number of child systems to several values beyond the available core count. Collect wall-clock runtimes from the sim_stats/ runtime diagnostics directory under data/ and assemble them into timing_scaling_table.csv with one row per excess-system count. Fit a least-squares linear model of wall-clock time versus the number of excess systems and record the slope and goodness of fit. Rationale: Nemesis uses socket-based child workers (not MPI), so wall-clock time stays flat while cores exceed systems and grows at worst linearly with the number of excess systems.

- **Nemesis** (Multi-scale integration framework whose wall-clock runtime is profiled across excess child-system counts; produces sim_stats/ diagnostics) — https://github.com/ErwanH29/nemesis

## Examples

```
cd examples/ && python basic_cluster/particle_initialiser.py && cd .. && python main.py --tend=0.1Myr  # repeat with increasing child-system counts; collect data/sim_stats/ runtimes and fit t ~ n_excess
```

## Evaluation signals

- Wall-clock time remains roughly unchanged while the number of available cores exceeds the number of systems.
- Beyond core saturation, the fitted slope of wall-clock time versus excess systems is positive and the linear fit residuals are near-zero (near-linear growth).
- timing_scaling_table.csv contains exactly one row per tested excess-system count with a runtime value drawn from sim_stats/.
- All runs use identical configuration: Ph4 for both parent and child, internal time-step 0.1, galactic field, stellar evolution and child collisions disabled.
- Runs complete without socket-worker crashes despite repeated child-integrator hibernation/resumption cycles.

## Limitations

- The linear scaling claim applies only once the number of systems exceeds available cores; below saturation, wall-clock time is expected to remain unchanged.
- Nemesis uses sockets rather than MPI for child subsystems because of heavy hibernation/resumption cycles; suspending or interrupting workers mid-communication can crash runs, especially with many children.
- Nemesis must be run from the same Python environment used to compile the C++ extension, or results will not be reproducible.
- Any parameter changed when resuming a run only triggers a warning — the simulation proceeds — so timings may silently mix configurations if resumption is used carelessly.
