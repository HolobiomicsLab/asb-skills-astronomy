# energy-conservation-error-analysis

## Summary

Assesses whether the multi-scale Nemesis integrator conserves energy as well as or better than a direct N-body code (Ph4) by running both on identical cluster-plus-planetary-system initial conditions and comparing energy-error behaviour alongside global- and local-scale outcomes.

## When to use

Use when validating a multi-scale integrator (e.g. Nemesis) against a direct N-body reference (Ph4): you need to quantify energy-error behaviour and confirm global- and local-scale indistinguishability over a controlled test window.

## When NOT to use

- When the parent and child codes are not the same integrator with identical code parameters (internal time-step), as the README warns this makes the comparison between models impossible.
- When the test window exceeds the cluster's crossing time — the README specifies 0.1 Myr precisely so systematic errors can emerge while remaining below crossing time.
- When stellar evolution, the galactic field or child collisions are enabled, since the comparison design turns these off for a clean integrator-vs-integrator performance check.

## Inputs

- Cluster initial conditions particle set generated by tests/cluster_test/initialise_cluster.py and stored in ICs/
- Nemesis run outputs: HDF5 particle snapshots (data/simulation_snapshot/), collision logs (data/collision_snapshot/) and runtime diagnostics (data/sim_stats/)
- Direct N-body reference outputs from the same run_cluster.py script with RUN_NEMESIS = 0

## Outputs

- Energy-error and global/local-scale comparison plots from tests/cluster_test/plot_cluster.py
- cluster_test_comparison.csv recording global- and local-scale agreement results

## How to apply

Generate cluster initial conditions with tests/cluster_test/initialise_cluster.py (saved under ICs/), then run two conditions of tests/cluster_test/run_cluster.py on identical parameters: RUN_NEMESIS=1 for the multi-scale code and RUN_NEMESIS=0 for direct Ph4. Use Ph4 as parent, child and direct integrator with the same code internal time-step 0.1, end time 0.1 Myr (below the cluster crossing time so systematic errors can emerge), bridge time 500 yr, diagnostic time 10000 yr, and galactic field, stellar evolution and child collisions turned off to isolate the integrator comparison. Nemesis writes HDF5 snapshots, collision logs and runtime diagnostics under data/ (simulation_snapshot/, collision_snapshot/, sim_stats/). Compare runs with tests/cluster_test/plot_cluster.py, judging energy-error behaviour together with global-scale (cluster) and local-scale (planetary system / asteroid) agreement, and record the outcome in cluster_test_comparison.csv.

## Examples

```
RUN_NEMESIS=1 python tests/cluster_test/run_cluster.py; RUN_NEMESIS=0 python tests/cluster_test/run_cluster.py; python tests/cluster_test/plot_cluster.py
```

## Evaluation signals

- Nemesis energy-error behaviour is at least as good as direct Ph4 — the paper claims 'improved energy conservation vs direct N-body'.
- Global-scale (cluster) outcomes from the Nemesis run are indistinguishable from the direct Ph4 run on identical initial conditions.
- Local-scale (planetary system / asteroid) outcomes, including collision behaviour, are indistinguishable between the two conditions.
- Both conditions used Ph4 with identical code internal time-step 0.1, end time 0.1 Myr, bridge time 500 yr, diagnostic time 10000 yr, and galactic field/stellar evolution/child collisions off.
- Results of the comparison are written to cluster_test_comparison.csv.

## Limitations

- Wall-clock time scales roughly as t_sim ∝ 1/δt_nem, where δt_nem is the time synchronisation between global and local scales, so tightening the bridge step for accuracy raises cost.
- Nemesis must be run from the same Python environment used to compile the C++ correction-kick extension.
- Resuming runs after changing simulation parameters proceeds with only a warning, which can silently invalidate a comparison.
- Children require a syst_id particle attribute with syst_id > 0 to be treated as child systems.
