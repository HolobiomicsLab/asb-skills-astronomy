# n-body-cluster-integration

## Summary

Integrate hierarchical astrophysical systems (star clusters containing planetary systems or binary children) with the Nemesis multi-scale framework in AMUSE: parents run on the cluster-optimised integrator Ph4, fast-evolving children are integrated in isolation, and the scales are synchronised via second-order kick-drift-kick correction kicks computed by compiled C++ routines.

## When to use

Use when simulating star clusters that embed fast-evolving subsystems (planetary systems, binaries, asteroids) where a direct N-body code like Ph4 over the whole system is too costly and extreme scale separation, tidal fields, and stellar evolution must be handled together.

## When NOT to use

- The system has no fast-evolving subsystems to decouple — a single direct N-body code (Ph4 over the whole particle set) is the simpler and more directly comparable choice
- The problem requires MPI-based parallel child integrators that cannot be interrupted — Nemesis uses sockets instead of MPI and suspends/resumes child workers, which conflicts with MPI's synchronised-process model
- Only secular single-system dynamics are needed (e.g. a von Zeipel–Lidov–Kozai test) without a cluster parent environment — a dedicated integrator run is more appropriate

## Inputs

- AMUSE particle set with children systems marked by syst_id > 0 (generated by particle_initialiser.py or tests/cluster_test/initialise_cluster.py, saved in ICs/)
- Simulation parameters as main.py command-line arguments (e.g. --tend, --dtbridge)
- Free parameters in src/globals.py (ASTEROID_RADIUS, EPS, MIN_EVOL_MASS, PARENT_RADIUS_COEFF/MIN/MAX, SPLIT_PARAM)

## Outputs

- HDF5 particle snapshots under data/simulation_snapshot/
- Collision event logs under data/collision_snapshot/
- Runtime diagnostics under data/sim_stats/

## How to apply

Categorise the particle set into parents and children (children need a syst_id > 0 attribute), then run the evolution procedure from src/nemesis.py: the global parent system is integrated with Ph4 (or Huayno with mode SHARED10_COLLISIONS for the ZKL test) while children are integrated in isolation by independent worker processes that communicate over sockets rather than MPI, because Nemesis relies on hibernation/resumption cycles of child integrators. Synchronisation between scales happens through second-order kick-drift-kitch correction kicks computed by C++ files compiled from src/cpp with make, and any change to _parent_worker, _stellar_worker, or _sub_worker must be mirrored in _worker_list. Set run parameters via main.py command-line arguments (e.g. --tend=1Myr --dtbridge=100yr) and free parameters in src/globals.py (EPS, PARENT_RADIUS_COEFF, SPLIT_PARAM, ASTEROID_RADIUS); the run automatically writes HDF5 particle snapshots, collision logs and runtime diagnostics under data/. Resume is automatic, but changing simulation parameters on resume only prints a warning while the simulation proceeds, so verify parameters before restarting.


## Evaluation signals

- A Nemesis run of a cluster with planetary systems yields results indistinguishable from the direct N-body code Ph4 on both the global (cluster) and local (planetary system/asteroid) scales, including energy-error behaviour
- Output directories are created automatically under data/ with simulation_snapshot/ HDF5 files, collision_snapshot/ logs, and sim_stats/ diagnostics populated
- In the ZKL test, subsystem splitting is validated and secular (von Zeipel–Lidov–Kozai) evolution is reproduced accurately across PARENT_RADIUS_COEFF models of 1e-5 au, 100 au and 1000 au
- Wall-clock time stays unchanged as long as the number of available cores exceeds the number of child systems, beyond which it grows at worst linearly
- Any worker change is reflected in _worker_list so all workers are handled properly at run time

## Limitations

- Nemesis uses sockets instead of MPI for child subsystems because it hibernates/resumes child integrators; interrupting or suspending MPI workers mid-communication can crash runs, especially with many children
- Runs can be resumed automatically, but if simulation parameters are changed on resume the simulation proceeds after only a warning message
- Stellar radii in snapshots correspond to ZAMS radius, not evolved radii
- Wall-clock time scales roughly as t_sim ∝ 1/δt_nem, where δt_nem is the time synchronisation between global and local scales
- The C++ correction-kick extension must be compiled from the same Python environment used to run Nemesis
