# swiglal-preprocessor-directive-integration

## Summary

Integrates SWIGLAL annotation directives into a generated SWIG interface by parsing the SWIG -xml syntax tree of LALSuite C header files with generate_swig_iface.py and inserting directives drawn from SWIGCommon.i, SWIGLALAlpha.i, and SWIGLALOmega.i.

## When to use

Use when wrapping C library headers (e.g. LALSuite) with SWIG and you need to automate annotation of the interface with SWIGLAL preprocessor directives before the second SWIG pass in -python or -octave mode.

## When NOT to use

- The target library is not built from C header files whose public constants, functions, and classes SWIG can enumerate via -xml mode
- The interface only needs basic SWIG wrappers without SWIGLAL-style annotation or LALSuite integration
- You are building SWIGLAL standalone — the README states SWIGLAL is fully integrated into LALSuite and cannot be built directly from its own repository

## Inputs

- LALSuite C header files
- XML syntax tree produced by SWIG -xml first pass
- SWIGCommon.i (common SWIG preprocessor directive definitions)
- SWIGLALAlpha.i and SWIGLALOmega.i (LAL-specific SWIG preprocessor directive definitions)

## Outputs

- Fully annotated SWIG interface file (e.g. SWIGTestLALPython.i) containing SWIGLAL directives covering every public constant, function, and class in the XML syntax tree
- Python or Octave wrapper code generated by the second SWIG pass

## How to apply

First run SWIG in its -xml mode over the LALSuite C header files, producing an XML syntax tree that enumerates every public constant, function, and class exported by the library (SWIG acting purely as a C header parser). Feed this XML tree to the Python script generate_swig_iface.py, which parses it and inserts SWIGLAL annotation directives into the interface definitions, drawing on the shared definitions in SWIGCommon.i and the LAL-specific definitions in SWIGLALAlpha.i and SWIGLALOmega.i. Write out the fully annotated SWIG interface file (e.g. SWIGTestLALPython.i for the test header) so it is ready for SWIG's second pass in -python or -octave mode, whose generated wrapper code (C for Python, C++ for Octave) is compiled into dynamically loadable modules. The whole workflow is implemented as macros and build rules in the GNU Autoconf/Automake build system used by LALSuite.

## Related tools

- **SWIG** (Run in -xml mode as a C header parser to produce the XML syntax tree, then again in -python or -octave mode to generate wrappers from the annotated interface)
- **Python** (Hosts generate_swig_iface.py, which parses the XML syntax tree and automates annotation of the interface file)
- **SWIGLAL** (Supplies the annotation directives (SWIGCommon.i, SWIGLALAlpha.i, SWIGLALOmega.i) inserted into the interface and the scripts that build Python and Octave interfaces)
- **LALSuite** (Provides the C header files being wrapped and the GNU Autoconf/Automake build system hosting the workflow macros) — https://git.ligo.org/lscsoft/lalsuite/blob/master/CONTRIBUTING.md
- **GNU Autoconf/Automake** (Implements the annotation workflow as macros and build rules in the LALSuite build system)

## Examples

```
swig -xml -o tree.xml SWIGTestLALPython.i; python generate_swig_iface.py tree.xml; swig -python SWIGTestLALPython.i
```

## Evaluation signals

- The annotated SWIG interface file exists and is non-empty
- The annotated interface file contains SWIGLAL annotation directives
- The annotated interface covers every public constant, function, and class present in the XML syntax tree
- SWIG's second pass in -python or -octave mode succeeds on the annotated interface and yields wrapper code that compiles into a dynamically loadable module importable via `import` in Python

## Limitations

- SWIGLAL is fully integrated into LALSuite and cannot be built directly from its own repository; build instructions live in the main LALSuite development repository
- The header files for LAL-specific definitions (SWIGLALAlpha.i, SWIGLALOmega.i) are specific to the LAL library, so other libraries would need their own directive definitions
- The generated wrapper code differs by target language: C for Python but C++ for Octave, so compilation must account for the language pairing
