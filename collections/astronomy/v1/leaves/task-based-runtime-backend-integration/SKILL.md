# task-based-runtime-backend-integration

## Summary

Builds FleCSI twice — once with the MPI backend (the only backend FleCSPH currently supports) and once with a task-based runtime backend (Legion distributed or Kokkos node-level) — and runs the identical Sod tube SPH configuration on both to produce a like-for-like wall-clock timing comparison of the FleCSI runtime backends.

## When to use

Decision support for choosing between FleCSI runtime backends (MPI vs Legion vs Kokkos) for FleCSPH particle simulations, when the goal is a controlled timing comparison using the same parameter file and particle count on each backend.

## When NOT to use

- When the objective is production-quality astrophysics output rather than backend benchmarking — the current FleCSPH only supports MPI, so a task-backend run is experimental
- When comparing algorithmic options within one backend (e.g. FMM MAC angle sweeps or N-body vs FMM), where runtime backend is not the variable under test
- When a single-node node-level comparison is desired with the distributed backend — Legion is distributed-memory and Kokkos is node-level, so they are not interchangeable baselines

## Inputs

- FleCSI repository (stable/flecsph branch, with git submodules checked out recursively)
- FleCSPH repository (git clone --recursive github.com/laristra/flecsph)
- Pre-configured Sod tube parameter file ../data/sodtube_t1_n1000.par
- Initial particle data in H5part format generated by app/id_generators/sodtube_1d_generator

## Outputs

- Two FleCSPH builds linked against different FleCSI runtime backends (MPI and Legion/Kokkos)
- Wall-clock execution times for hydro_1d runs on each backend
- backend_timing_comparison.csv containing timing entries, backend identifiers, particle counts, and run configurations for both backends

## How to apply

Configure and build FleCSI from the stable/flecsph branch twice: once with -DFLECSI_RUNTIME_MODEL=mpi and once with a task-based backend (Legion for distributed-memory, Kokkos for node-level) selected at CMake configure time, following the paper's manual build (cmake with -DENABLE_OPENMP=OFF, -DCXX_CONFORMANCE_STANDARD=c++17, -DENABLE_METIS=ON, ENABLE_UNIT_TESTS=ON, then make -j and make install). Build FleCSPH against each FleCSI build. Generate identical initial data for both runs by copying ../data/sodtube_t1_n1000.par to sodtube.par and running app/id_generators/sodtube_1d_generator, keeping particle count and all physics parameters unchanged. Execute app/driver/hydro_1d sodtube.par on each backend under comparable resource allocation, record wall-clock time for each run, and assemble backend identifiers, particle counts, run configurations, and timings into backend_timing_comparison.csv. The rationale is that FleCSPH is architecturally consistent with both MPI and task-based runtimes, so swapping backends requires only reconfiguring FleCSI, not changing the simulation setup.

```

```

## Evaluation signals

- backend_timing_comparison.csv contains timing entries for BOTH the MPI backend and the task-based backend for the same Sod tube configuration
- Both runs complete the hydro evolution to the end time specified in the parameter file (Sod tube t1 n1000 configuration)
- Both runs use identical initial data (same particle count and physics parameters from sodtube_t1_n1000.par) generated by the same sodtube_1d_generator run
- Both executions use comparable resource allocation so timings are like-for-like
- Each backend build is verified by ENABLE_UNIT_TESTS=ON unit tests passing after the make -j / make install cycle

## Limitations

- The current version of FleCSPH only supports the MPI backend and does not take advantage of all FleCSI features, so the task-backend path is future work rather than a supported configuration
- FMM timing strongly depends on the MAC angle, so SPH+gravity timing comparisons must fix the MAC angle across backends
- The article's Spack module-support instruction is truncated mid-sentence ('Use the following command to install _module_ support for spack an'), so the Spack route may need external documentation
