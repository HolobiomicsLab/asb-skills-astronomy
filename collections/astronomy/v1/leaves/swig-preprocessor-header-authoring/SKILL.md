# swig-preprocessor-header-authoring

## Summary

Author C headers with SWIG preprocessor directives (e.g. SWIGCommon.i, SWIGPython.i, SWIGOctave.i, SWIGLALAlpha.i, SWIGLALOmega.i) that further integrate generated wrappers with a C library such as LALSuite, and feed them alongside the annotated SWIG interface during the second-pass -python/-octave invocation.

## When to use

Use when building SWIG bindings for a C library and you need shared wrapper-integration code split into common, language-specific, and library-specific preprocessor headers included by the SWIG interface files.

## When NOT to use

- When bindings for the target language already exist (e.g. via ctypes/cffi or a maintained wrapper package) and only need installation, not authoring
- When the goal is only the first SWIG -xml parsing pass or automated header annotation via generate_swig_iface.py — those precede, and do not require, preprocessor-header authoring

## Inputs

- SWIG preprocessor header files (.i) written in C with SWIG preprocessor directives (SWIGCommon.i, SWIGPython.i, SWIGOctave.i, SWIGLALAlpha.i, SWIGLALOmega.i)
- Annotated SWIG interface files generated by generate_swig_iface.py from the SWIG -xml syntax tree
- Public C header files of the target library (e.g. LALSuite C headers)

## Outputs

- Integration definitions that SWIG expands during the second pass into C wrapper code (Python target) and C++ wrapper code (Octave target)
- Doxygen-documented definitions for the common and library-specific headers

## How to apply

Write header files in C containing SWIG preprocessor directives: a common definitions header (SWIGCommon.i), per-language headers for the target scripting languages (SWIGPython.i for Python, SWIGOctave.i for Octave), and library-specific headers (SWIGLALAlpha.i and SWIGLALOmega.i for the LAL library). Structure the split so shared wrapper logic lives in the common header, language-specific integration in the per-language headers, and library-specific definitions in the SWIGLAL* headers; this mirrors SWIGLAL's layering and keeps language backends swappable. Include these headers from the annotated SWIG interface files produced by generate_swig_iface.py, so that when SWIG runs its second pass in -python mode (emitting C wrapper code) or -octave mode (emitting C++ wrapper code), the directives expand to integrate the wrappers with the library's memory management and constants/functions/classes. Document the definitions provided by the common and library-specific headers through the library's Doxygen documentation, as SWIGLAL does for SWIGCommon.i, SWIGLALAlpha.i, and SWIGLALOmega.i. Validate by confirming the second pass produces non-empty wrapper sources for each requested language mode that expose the library's public constants, functions, and classes, ready to be compiled into dynamically loadable modules.

## Related tools

- **SWIG** (Expands the preprocessor directives in the .i headers while generating C (Python) and C++ (Octave) wrapper code during the second pass) — http://www.swig.org/
- **SWIGLAL** (Provides the exemplar header set (SWIGCommon.i, SWIGPython.i, SWIGOctave.i, SWIGLALAlpha.i, SWIGLALOmega.i) being authored) — ElsevierSoftwareX/SOFTX_2020_119
- **LALSuite** (C library whose constants, functions, and classes the headers integrate the wrappers with) — https://git.ligo.org/lscsoft/lalsuite/blob/master/CONTRIBUTING.md
- **GNU Autoconf/Automake** (Build system macros and build rules that drive SWIG with the headers for each language target)

## Examples

```
swig -python -o swiglal_wrap.c SWIGTestLALPython.i  # interface includes SWIGCommon.i, SWIGPython.i, SWIGLALAlpha.i
```

## Evaluation signals

- For each requested language mode (-python, -octave), the corresponding generated wrapper source file exists, is non-empty, and wraps the library's public constants, functions, and classes
- Common definitions are not duplicated: language-specific code appears only in SWIGPython.i/SWIGOctave.i, and library-specific code only in SWIGLALAlpha.i/SWIGLALOmega.i
- Second-pass SWIG invocation with the headers included succeeds in both -python mode (C wrapper output) and -octave mode (C++ wrapper output)
- Definitions in SWIGCommon.i, SWIGLALAlpha.i, and SWIGLALOmega.i are covered by the library's Doxygen documentation
- Generated wrappers compile into dynamically loadable modules importable in the target language (e.g. via `import` in Python)

## Limitations

- SWIGLAL is fully integrated into LALSuite and cannot be built directly from its own repository; the headers only take effect within the LALSuite build system
- The headers add code 'to further integrate the wrappers' on top of basic SWIG wrappers — they do not replace the need for the two-pass SWIG workflow and generate_swig_iface.py annotation step
- Octave targets emit C++ wrapper code while Python targets emit C, so directives must account for different generated-language semantics per backend
