# radio-transient-data-downsampling

## Summary

Time-domain downsampling of dedispersed radio time series by averaging samples over a configured number of integration steps, as implemented in AMBER's Integration stage (TRASAL/Integration, OpenCL) to raise pulse SNR before detection.

## When to use

Use when dedispersed time series (e.g. AMBER's 5120 DM trials) must be averaged over integration steps (6 in the ARTS survey) to boost single-pulse SNR before thresholding.

## When NOT to use

- Input is raw (pre-dedispersion) radio data — dedispersion must run first to compensate for frequency-dependent dispersion by interstellar free electrons
- Input is already an integrated/downsampled series — re-integrating would further reduce time resolution without a survey justification
- Data are not radio time series (e.g. LOFAR HDF5 raw records not yet run through AMBER's pipeline stages)

## Inputs

- dedispersed time series from the AMBER Dedispersion stage (one series per DM trial; 5120 DM trials in the ARTS survey configuration)
- pipeline configuration file generated by amber.sh tune, specifying the number of integration steps (6 for ARTS)

## Outputs

- integrated (downsampled) time series, e.g. integrated_series.bin, with time dimension reduced by the integration factor and DM dimension preserved
- performance statistics file emitted by AMBER after each successful execution

## How to apply

Load the dedispersed time series produced by AMBER's Dedispersion stage for all dispersion measure trials, then run the Integration stage (TRASAL/Integration library, executed through AMBER's OpenCL kernel) averaging samples over the configured number of integration steps — 6 in the ARTS survey configuration, where the search space spans 5120 DMs. Write the downsampled series (e.g. to integrated_series.bin), preserving the DM dimension while shortening the time dimension by the integration factor. Because AMBER kernels are auto-tuned, tune the Integration module to the execution hardware via the AMBER_setup script's 'tune' mode against a scenario description before running, so OpenCL work-group sizes and serial processing per thread fit the GPUs (the ARTS cluster uses 3 GPUs per node). The integration factor is a survey-level decision point: larger factors widen detectable pulse widths but reduce time resolution.

## Examples

```
amber.sh tune examples/scenario.sh ${INSTALL_ROOT}/confs
```

## Evaluation signals

- integrated_series.bin exists and is readable after the run
- time dimension of the output is reduced by exactly the integration factor (6 in the ARTS configuration) relative to the input dedispersed series
- DM dimension is preserved: 5120 DM trials in, 5120 DM trials out
- AMBER exits successfully and emits its two post-run output files (candidate detections and performance statistics)
- tuned configuration files pass the AMBER_setup 'test' mode check for the scenario

## Limitations

- No quantitative metric threshold is reported in the paper; correctness is judged by structural consistency (time reduced by the integration factor, DM dimension preserved)
- OpenCL is a hard dependency — the pipeline cannot run without a working OpenCL environment
- Running amber.sh tune deletes previously generated configuration files in the target directory
- OpenCL kernels require many low-level parameters (work-group size, local memory usage, serial processing per thread), so performance depends on auto-tuning to the specific hardware
