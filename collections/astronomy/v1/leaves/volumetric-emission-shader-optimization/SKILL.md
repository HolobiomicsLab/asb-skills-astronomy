# volumetric-emission-shader-optimization

## Summary

Renders the tricubic-smoothed 3-D comet coma number-density volume in Blender Cycles using a volumetric emission shader instead of volumetric scattering, trading physical accuracy for substantially faster path-traced rendering of the dust- and gas-environment optical model.

## When to use

Use when a smoothed coma number-density volume (e.g. EXR from ComaCreator's ToBlender step) must be rendered in Cycles and qualitative visual output suffices, so the faster volumetric emission variant is preferred over scattering.

## When NOT to use

- Quantitative radiometric fidelity is required (e.g. for imaging-instrument characterisation or photometric calibration), where the less accurate emission shader should be replaced by volumetric scattering
- The input is not a volumetric density field (e.g. a bare surface model without a ComaCreator-generated coma), so there is no coma volume to render
- Rendering outside Cycles — ComaCreator's rendering path states 'Only Cycles support'

## Inputs

- Tricubic-smoothed 3-D comet coma number-density volume (EXR, written by ComaCreator's ToBlender step)
- Comet nucleus shape model (e.g. OBJ mesh such as data/comet3.obj)
- SISPO scene configuration JSON with options and ComaCreator/JetCreator parameters (T_gas=210.0, sample_points [64,64,64], bbox_lower/upper [-5,-5,-5]/[5,5,5])

## Outputs

- Rendered image of the comet nucleus embedded in a diffuse coma (e.g. comet_coma_render.png)
- Cycles path-traced scene with the coma volume bound to the emission shader density input

## How to apply

Load the smoothed 3-D number-density field (generated by ComaCreator's KGasSimulation on a cubic bounding box, e.g. bbox -5 to 5 with 64x64x64 sample_points) into the Blender scene as a volumetric density input, then assign the volumetric emission shader instead of the volumetric scattering shader when the view does not require physically based light scattering through the coma. Set up the comet nucleus mesh (optionally decimated, e.g. to 1% of ~3M triangles via 'decimate_percentage': 1.0), illumination and camera parameters from the SISPO scene configuration, and render with the Cycles path-tracing engine, which is the only engine SISPO's ComaCreator pipeline supports. Emission-mode rendering is faster but less accurate than scattering, so choose it for quick previews or large scenario sweeps and switch to volumetric scattering when photorealistic light interaction matters. Verify the result qualitatively against the reference appearance of a nucleus embedded in a diffuse coma, comparable to Fig 9 of the manuscript.

## Evaluation signals

- Output image (e.g. comet_coma_render.png) exists and is a valid image file
- Image qualitatively shows a comet nucleus embedded in a diffuse coma, comparable to Fig 9 of the manuscript
- Render completes without error and measurably faster than the volumetric-scattering variant on the same 64x64x64-sample volume
- The EXR density volume loads into Cycles with its bounding box (e.g. -5 to 5) matching the scene scale
- Number-density values are visibly mapped to the shader density input (brighter regions trace jet/coma structure)

## Limitations

- Emission rendering is faster but less accurate than volumetric scattering, so it should not be used where physical light-scattering behaviour is needed
- The ComaCreator pipeline runs only with Cycles ('Only Cycles support')
- EXR volume files can grow to ~1 GB, a storage bottleneck acknowledged by the developers
- ComaCreator is explicitly not for real science — 'should be only used for creating pretty realistic looking pictures' — and is in a permanent development stage with bugs
