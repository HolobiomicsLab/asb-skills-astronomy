# surrogate-vs-fiducial-timing-comparison

## Summary

Benchmarks the wall-clock cost of evaluating a gravitational-wave surrogate model against fiducial EOB waveform generation (EOB-LAL) as a function of sampling rate, quantifying the speedup (O(mL + m*c_fit) scaling, ~2,300x at 2,048 Hz).

## When to use

Use when you need to quantify how much faster a surrogate waveform model evaluates than the fiducial solver (e.g., EOB-LAL) across sampling rates, or to verify linear-in-L surrogate prediction cost.

## When NOT to use

- When the goal is waveform accuracy validation (faithfulness, mismatches) rather than computational cost — this skill only measures timing and speedup.
- When the fiducial waveform family is not generated by a differential-equation solver (e.g., waveforms already produced by a surrogate or lookup table), since the EOB-LAL timing baseline would not be meaningful.
- When a single fixed sampling rate suffices and no scaling-with-L verification is needed; the sweep across rates is the core of this skill.

## Inputs

- Loaded gwsurrogate surrogate model (e.g., EOBNRv2 time-domain surrogate with m greedy elements)
- Binary parameters for a generic waveform evaluation (mass ratio, spins as applicable)
- EOB-LAL fiducial waveform generator (LIGO Analysis Library EOB solver)
- Sweep of sampling rates (e.g., up to 2,048 Hz) defining the number of time samples L

## Outputs

- Per-rate wall-clock timings for surrogate evaluation and EOB-LAL generation
- Speedup ratios (surrogate / EOB-LAL) at each sampling rate
- Scaling check confirming surrogate cost is linear in L (O(mL + m*c_fit))
- timing_comparison.csv with timings, speedup factors, and scaling results

## How to apply

First pull and load the surrogate via gwsurrogate.catalog.pull and gwsurrogate.LoadSurrogate (e.g., an EOBNRv2 surrogate built with m=10 greedy-selected empirical-interpolant elements). Generate fiducial effective-one-body waveforms for the same binary parameters using the EOB solver as implemented in the LIGO Analysis Library (EOB-LAL code) to establish the timing baseline. Sweep the sampling rate from low rates up to 2,048 Hz; at each rate, time surrogate evaluation for a generic parameter choice and time EOB-LAL generation for the same parameters. Compute the surrogate-to-EOB-LAL speedup ratio per rate and verify surrogate cost follows the O(mL + m*c_fit) prediction, i.e., linear in the number of time samples L with m << L. Write per-rate timings, speedup factors, and the scaling check to timing_comparison.csv.

## Examples

```
import gwsurrogate; gwsurrogate.catalog.pull('EOBNRv2'); sur = gwsurrogate.LoadSurrogate('EOBNRv2'); t, h, dyn = sur(q, dt=1/2048, f_low=f_low)
```

## Evaluation signals

- Measured speedup at 2,048 Hz is approximately 2,300x over EOB-LAL
- Overall speedups fall between 2 and nearly 4 orders of magnitude (consistent with the reported 'more than 3 orders of magnitude faster' result)
- Surrogate evaluation wall-clock time is linear in the number of samples L, matching the O(mL + m*c_fit) prediction with m << L
- Same binary parameters and sampling rates are used for both surrogate and EOB-LAL timings, so the speedup ratio is apples-to-apples
- timing_comparison.csv contains one row per sampling rate with surrogate time, EOB-LAL time, and speedup factor

## Limitations

- Speedup depends strongly on the sampling rate: between 2 and almost 4 orders of magnitude, so a single rate figure (e.g., 2,300x at 2,048 Hz) should not be extrapolated to other rates
- The m=10 greedy-element surrogate is specific to its fiducial EOB family (nonspinning, durations up to 10^5M, mass ratios 1–10); results do not transfer to precessing or high-mass-ratio models
- gwsurrogate C-extension modules require NumPy C-API headers at build time; NumPy 1.x vs 2.x build/runtime compatibility must be handled (e.g., conda create with 'numpy<2.0')
